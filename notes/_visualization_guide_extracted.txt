Visualization Style Guide
ODE IVP Project
Applied to every figure that appears in the report or slides. The goal is not aesthetics for their own sake: a
figure is a piece of evidence, and evidence must be legible, honest, and self-explanatory.

Rules
1. Log-log for error-vs-step plots
When plotting error against step size h (or ∆t), use logarithmic axes on both. This is non-negotiable: the
whole point is that order of convergence appears as a straight line whose slope you can read and compare to
theory.
ax. loglog (h_values , errors , "o-")
# add the theoretical slope for comparison
h_lin = np. logspace (-3, -1, 20)
ax. loglog (h_lin , C * h_lin **1.0 , "k--", label =" order 1")

Always overlay the theoretical slope. An order-1 plot without the reference line is a claim without a benchmark.
Confidence band on the fitted line. The slope is the claim; report it with its uncertainty. np.polyfit with
cov=True returns the slope, its standard error, and the covariance the band is built from:
coef , cov = np. polyfit (np.log( h_values ), np.log( errors ), 1, cov=True)
slope , slope_err = coef [0] , np.sqrt(cov [0, 0])
lx = np. linspace (np.log( h_values .min ()), np.log( h_values .max ()), 50)
line = coef [0]* lx + coef [1]
se = np.sqrt(cov [1 ,1] + 2* lx*cov [0 ,1] + lx **2* cov [0 ,0])
ax. loglog (np.exp(lx), np.exp(line), "k--", label ="fit")
ax. fill_between (np.exp(lx), np.exp(line - 1.96* se),
np.exp(line + 1.96* se), color ="gray",
alpha =0.3 , label ="95% band")

A band only means something if the data is repeatable. A deterministic convergence table gives a narrow band
(a fit diagnostic); a Monte-Carlo claim needs repeats across seeds, and the spread across repeats is the honest
band.

2. Always label axes and units
• Axis label: quantity (unit). E.g. step size h [s], global error [---].
• Title: state what the figure shows AND what conclusion it supports.
• Every figure gets a caption in the report that says what is shown and why it matters. “Figure 3. Convergence” is not a caption.

3. Use colour responsibly
• Never use rainbow / jet colormaps. They are illegible in print and misleading (perceptually nonuniform). Use viridis, plasma, or categorical palettes (tab10).

• In error plots, use o- markers with lines, not bare markers.

4. Annotate the physics/math
• Mark the interesting region (e.g. the h at which stability kicks in) with a vertical line or shaded patch, and
label it.
• If there is a round-off floor in a log-log plot, point at it: “error flattens at h ≈ 10−6 due to double-precision
round-off”. That is a finding, not noise.

5. Reproducibility
• Save every figure from run_all.py with a fixed seed and fixed file name: fig05_order_euler.png.
No timestamps or machine-specific junk in filenames.
• DPI ≥ 150 for the report; ≥ 200 for slides.
• Every number quoted in the text must be reproducible from a figure or a printed line in the code output.

6. Time-series sanity
• For ODE solutions over time, always show a reference (analytic or high-accuracy) when one exists.
• When comparing integrators, use the SAME time axis and SAME line styles, and a legend.

7. Cost–accuracy evidence (Learning Outcome D)
• Plot error versus cost, not error versus nothing: the horizontal axis is the measured cost (wall time, righthand-side evaluations, Newton iterations, or accepted/rejected steps), the vertical axis the achieved accuracy against your reference solution.
• Name the cost measure before you quote it. “Our implicit method is faster” is not a result; “at a final-time
error of 10−6 , implicit Euler took 0.8 s and RK4 took 3.1 s on the same machine” is.
• Match the target first. Bring both methods to the same error level before comparing costs — a fast method
at a loose tolerance proves nothing. State the target in the caption.
• Say what you did not count (Jacobian assembly and factorisation, setup, compilation, plotting) and hold
it constant across the methods being compared.
• The negative result is still a result. If the method you expected to win lost, plot it and say so — that is a
complete answer.
